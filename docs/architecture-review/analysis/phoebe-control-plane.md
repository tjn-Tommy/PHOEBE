# Control Plane Review — PHOEBE (gateway / task_manager / lease / device_manager / capability / di / plugin / errors / factory)

## 1. Responsibility map

**Command path (observed, end to end).** The Qt thread calls `Gateway.submit_threadsafe(envelope, loop)`, which is a thin `run_coroutine_threadsafe` wrapper (phoebe/core/gateway.py:52-55) onto the dedicated `LoopThread` loop (phoebe/app/bootstrap.py:79-108). `Gateway.submit` splits traffic: `pause`/`resume`/`cancel` are hard-coded builtins that call `TaskManager.request_*` directly, extracting `payload["task_id"]` by hand and mapping `KeyError`/any `Exception` to a rejected `CommandAck` (gateway.py:40, 57-77); everything else goes to `TaskManager.dispatch` (gateway.py:47-50). The Gateway is otherwise stateless — all routing intelligence lives in `TaskManager`.

`TaskManager.dispatch` (phoebe/core/task_manager.py:198-234): (1) look up the `PluginSpec` by command in the registry; (2) `validate_boundary(spec.config_type, cmd.payload)` — the contract choke point (task_manager.py:204, phoebe/core/contracts.py:81-91, a JSON round-trip that keeps strict-mode semantics); (3) `spec.instantiate()` + bound entrypoint (phoebe/core/plugin.py:41-45); (4) `DependencyResolver.resolve` parses the entrypoint signature for `Depends` defaults, maps each annotation through the explicit protocol→kind table `_KIND_BY_PROTOCOL` (phoebe/core/di.py:26-34, filled by `instruments/protocols.py` via `register_capability_kind`), then binds by the documented priority: `Depends(role=...)` → `[plugins."<id>".bindings]` table → unique-by-kind → `PhoebeConfigError` fail-fast (di.py:77-111); (5) `DeviceManager.try_acquire_all(task_id, reqs)` — a fully synchronous, await-free scan of the ownership table `_owners`, rolling back all leases granted in the call on any conflict (phoebe/core/device_manager.py:123-165), which makes acquisition atomic on the single loop exactly as spec §6.2 requires (refactor.md:738-763). On `LeaseUnavailableError`: `REJECT` policy returns `accepted=False, reason="423 locked by <task>"` (task_manager.py:220-222); `QUEUE` policy creates a `_RunRecord`, appends a `_PendingRun`, publishes a `QUEUED` `RunStateEvent`, and acks `queued=True` (task_manager.py:223-229). On success, `_start_run` spawns `asyncio.create_task(self._execute(...))` (task_manager.py:236-242) and the ack returns immediately.

**Run execution.** `_execute` (task_manager.py:296-373) creates the run dir, a per-run loguru JSONL sink filtered by task_id, a `RunWriter`, and a `RunContext`; writes `run.json` (manifest with config hash, app-config hash, git state, per-instrument identity — task_manager.py:375-402) and `baseline_pre.json`; `stage()`s each controller; transitions QUEUED→RUNNING; then awaits the plugin entrypoint with `config=..., ctx=..., **{param: controller}` (task_manager.py:326-331). Note the injected objects are the raw `InstrumentController` instances from `DeviceManager._controllers` (task_manager.py:321-322) — the "capability view" of spec §7.3 is nominal: the plugin's annotation is a Protocol, but the object is the full controller.

**State machine.** `_RunRecord.set_state` enforces `_TRANSITIONS` (task_manager.py:44-55, matching refactor.md:842-850 exactly) and publishes a `RunStateEvent` on every legal transition (task_manager.py:150-158). Pause: `request_pause` sets PAUSING + the `pause_requested` event (task_manager.py:245-248); the transition to PAUSED happens inside the plugin's next `ctx.checkpoint`, which also touches all leases as heartbeat, waits on `resume_event`, re-raises cancellation, and yields the loop (task_manager.py:105-116). Cancel: `request_cancel` handles the QUEUED case by list-filtering `_queue` and jumping to ABORTED; otherwise STOPPING + token cancel + `resume_event.set()` to unblock a paused checkpoint, plus fire-and-forget `stop()` tasks on all leased controllers, fetched by reaching into `self._dm._lease_sets` (task_manager.py:258-273). Completion/failure funnel through `finally`: bounded (`asyncio.timeout(cleanup_timeout_s)`) reverse-order `stop()`/`safe_state()`/`unstage()`, throttle flush, `writer.aclose()`, `baseline_post.json`, `dm.release`, sink removal, then the **terminal re-broadcast** `RunStateEvent(reason="final")` after leases are released, then `_maybe_start_next_queued()` (task_manager.py:349-373). The UI gates on the literal string comparison `event.reason == "final"` (phoebe/ui/main_window.py:336).

**Suspender.** A per-config bus subscriber that pauses all RUNNING tasks when a watched metric leaves range and resumes only those it auto-suspended after `grace_s` in range (task_manager.py:434-501), started/stopped by `TaskManager` (task_manager.py:422-431, wired in bootstrap.py:69).

**Leases.** `Lease` is a contract row; `LeaseSet` adds per-instrument refcounts, heartbeat timestamps, and a `merge` that shares the parent's slot dict for inheritance (phoebe/core/lease.py:32-114). `DeviceManager` owns `_owners` (instrument→lease), `_lease_sets` (task→LeaseSet), the TTL reaper (`_reap_once` stops + safe_states expired holders' devices and reclaims rows, device_manager.py:201-221), health broadcasting, and startup identity verification against the config (device_manager.py:66-78).

**Capability/factory.** `CapabilityRegistry.invoke` is the per-controller validation choke point: dict requests go through `validate_boundary`, local objects are type-checked (`CapabilityContractError` on mismatch), `context.ensure_not_cancelled()` runs before the handler, and responses are re-validated via `TypeAdapter` when `validate_responses` is on (phoebe/core/capability.py:115-133). `ControllerFactoryRegistry` keeps (kind,vendor,model)→factory plus a separate by-kind sim table; `backend="sim"` short-circuits to the sim factory (phoebe/core/factory.py:49-81).

**Where state lives.** Per-process singletons: the module-global `plugin_registry` (plugin.py:88), the global `_KIND_BY_PROTOCOL` table (di.py:26), and the global lease-id counter (lease.py:25). Everything else hangs off the `AppRuntime` composition root (bootstrap.py:42-76). Concurrency: the entire control plane runs on the one loop thread; the bus asserts cross-thread publish (phoebe/core/bus.py:113-118); the only cross-thread entry is `submit_threadsafe`.

## 2. Strengths

- **Await-free atomic lease acquisition** with explicit rollback of the current call's grants and inherited increfs (device_manager.py:135-165) is exactly the no-hold-and-wait design the spec demands (refactor.md:747-749); deadlock is structurally excluded and the code matches the spec's pseudocode closely.
- **Single checkpoint primitive** unifying pause point, cancel point, heartbeat, and loop yield (task_manager.py:105-116) keeps plugin code free of locks/sleeps — the shipped plugin genuinely contains none (phoebe/plugins/tpa_multiplier.py:57-78).
- **Cleanup ordering and degradation discipline**: hardware first (reverse order, `safe_state()` only on failure), then data plane, then resources, each step in its own try/except so a cleanup fault never leaks the sink or leases on the normal path (task_manager.py:349-372), matching refactor.md:916-950. The lease-release-before-final-rebroadcast ordering (task_manager.py:368-372) is a small but genuinely well-thought-out fix for the "next dispatch races the release" problem.
- **DI fail-fast with explicit protocol→kind registration** rather than `isinstance` sniffing (di.py:26-34, 82-110); ambiguity errors name the exact TOML fix (di.py:106-110). Errors surface at dispatch, not mid-run.
- **Validation choke points are real, not aspirational**: dispatch (task_manager.py:204), capability invoke (capability.py:125-132), config parse (phoebe/core/config.py:128), all through the same `validate_boundary`.
- **Provenance capture** — manifest with config hash, app-config hash, git commit/dirty, and live device identities queried at run start (task_manager.py:375-402) — is better than the spec sketch.
- **Identity verification at connect** treating the device, not the config, as source of truth (device_manager.py:66-78).

## 3. Issues

**H1 (High) — cancel while a pause is pending misclassifies the run as FAILED.** `request_cancel` sets STOPPING and `resume_event`, but never clears `pause_requested` (task_manager.py:258-268). If cancel arrives after `request_pause` but before the plugin reaches its next checkpoint, that checkpoint enters the pause branch and calls `record.set_state(RunState.PAUSED)` from STOPPING — an illegal transition that raises `RuntimeError` (task_manager.py:110, 153-154). It escapes the plugin as a generic exception, so `_execute` publishes an `ErrorEvent`, transitions to **FAILED** instead of ABORTED, and invokes `safe_state()` (task_manager.py:339-348, 354-355). Impact: wrong terminal state in the record/UI/manifest and a spurious error event for a plain user cancel. Trigger: UI user clicks Pause then Cancel within one checkpoint interval — an entirely normal interaction. The test suite covers pause→resume→cancel but not pause→cancel (tests/test_e2e_sim.py:142-165).

**H2 (High) — any failure before RUNNING hits an illegal QUEUED→FAILED transition and produces a zombie run.** `_write_manifest`, `_write_baseline`, and `stage()` all run while the record is still QUEUED (task_manager.py:326-330); `_TRANSITIONS[QUEUED]` permits only RUNNING/ABORTED (task_manager.py:45). If `stage()` raises (a routine hardware fault at run start), the `except Exception` handler's `set_state(RunState.FAILED)` itself raises `RuntimeError` (task_manager.py:348, 153-154). The `finally` still releases leases, but the record is left permanently non-terminal in QUEUED, the "final" rebroadcast carries `state=QUEUED` (task_manager.py:370-372), `active_tasks()` includes the task forever (task_manager.py:286-287), and the RuntimeError leaves `_execute` as an unretrieved task exception.

**H3 (High) — run-setup code sits outside the try/finally: setup failure leaks leases with no terminal event.** `new_run_dir`/`mkdir`, `logger.add`, `RunWriter` construction and `writer.start()` all execute before the `try` at task_manager.py:325 (task_manager.py:300-315). An OSError there (disk full, permissions) aborts `_execute` with leases still held (reclaimed only by the 600 s TTL reaper), the loguru sink leaked if added, and no `RunStateEvent` of any kind — directly violating the spec's "no step may leak leases or sinks" rule (refactor.md:950).

**H4 (High) — reaper reclamation neither terminates the run nor protects the ownership table from double release.** `_reap_once` pops `_owners` rows and the task's `LeaseSet` (device_manager.py:212-221) but does not touch the still-running `asyncio.Task` or `_RunRecord` — the run continues executing against instruments it no longer owns and the UI shows RUNNING forever. Worse: when that run eventually finishes, `_execute` calls `self._dm.release(task_id, leases)` with its original `LeaseSet`, whose `decref`→0 does `self._owners.pop(iid, None)` unconditionally (task_manager.py:368; device_manager.py:167-172) — if a new task acquired the instrument after reaping, the *new holder's* row is deleted and a third task can then co-acquire the same instrument. Trigger: any plugin whose single awaited operation exceeds `lease_ttl_s` (heartbeats occur only at checkpoints, task_manager.py:107), i.e. a healthy long acquisition gets reaped, then the corruption path follows. Consequence class is hardware-unsafe (two runs driving one device), on a fault-path trigger. Fix surface would be an owner/lease-id identity check in `release` plus reaper→TaskManager notification — flagged only, per mandate.

**H5 (High) — under `QUEUE` policy, queued runs stall forever if leases are freed by the reaper.** `_maybe_start_next_queued` is called only from `_execute`'s finally (task_manager.py:373); the reaper frees devices without any callback (device_manager.py:212-221). Scenario: overnight batch (the stated purpose of QUEUE, task_manager.py:60), one run hangs and is reaped — every queued run behind it waits indefinitely even though all devices are free. Silent stall of the exact workload the feature exists for.

**M1 (Medium) — cleanup timeout doesn't cover the data-plane/baseline steps.** `asyncio.timeout` wraps only the controller stop/unstage loop (task_manager.py:351-356); `writer.aclose()` and `_write_baseline` (which awaits `get_snapshot()` on possibly-dead controllers, task_manager.py:361-367, device_manager.py:110-120) are unbounded. A hung snapshot delays lease release and the final rebroadcast indefinitely — the Start button never re-enables.

**M2 (Medium) — queue is not FIFO and can starve multi-instrument runs.** `_maybe_start_next_queued` starts any startable pending run, skipping blocked ones (task_manager.py:408-419). A queued run needing SLM+OSA is overtaken indefinitely by a stream of OSA-only runs. Spec says "minimal FIFO" (refactor.md:882); the deviation (head-of-line-blocking avoidance vs. starvation) is undocumented.

**M3 (Medium) — lease inheritance (§6.3) is implemented but unreachable.** `try_acquire_all(parent=...)`, `LeaseSet.merge/incref`, and `parent_lease_id` exist (device_manager.py:123-165, lease.py:97-114) but no production caller ever passes `parent` (only task_manager.py:218, 411 — both parentless; sole exercise is tests/test_lease_and_di.py:59). The spec's requirement that `InvocationContext` carry the current `LeaseSet` (refactor.md:771) is unmet — the protocol exposes only `task_id`/`ensure_not_cancelled` (capability.py:52-59). A sub-flow dispatched as its own task would 423 against its parent today; only same-coroutine composition works.

**M4 (Medium) — encapsulation leaks across the manager boundary.** `request_cancel` reads `self._dm._lease_sets` directly (task_manager.py:270); `Suspender` reads `self._tm._records` (task_manager.py:487, 497). Both bypass any public API, coupling TaskManager to DeviceManager internals and making a future process split (web backend) harder.

**M5 (Medium) — DI resolver snapshots the device inventory at construction.** `role_map()`/`kind_index()` are materialized once into `DependencyResolver` (task_manager.py:189-193; di.py:60-66). Any post-startup inventory change (reconnect with different capabilities, added device) is invisible to resolution. Blocks hot-reconnect scenarios.

**M6 (Medium) — the control protocol is stringly typed.** 423 is prose inside `CommandAck.reason` ("423 locked by ...", task_manager.py:221-222; even the test greps for `"423"`, tests/test_e2e_sim.py:137); the terminal-final contract is the magic string `reason == "final"` on a field that elsewhere carries human text like "pause requested" (task_manager.py:371, 247; ui/main_window.py:336). `CommandAck` has no error-code field (gateway.py:32-37). A Vue/Tauri frontend would have to parse English prose to distinguish busy/invalid/unknown.

**M7 (Medium) — error context is dropped at the event boundary.** `_execute` publishes only `type(exc).__name__` + `str(exc)` (task_manager.py:342-345); `InstrumentError.instrument_id`/`last_command` (phoebe/core/errors.py:13-17) are never mapped into `ErrorEvent.instrument_id` (events.py:103-107), so the UI cannot attribute a failure to a device even though both sides of the pipe have the field.

**M8 (Medium) — `_records` is never evicted** (task_manager.py:187, 224, 232): terminal records accumulate for the process lifetime; `active_tasks()` scans them all (task_manager.py:286-287). Matters precisely for the long overnight QUEUE sessions.

**L1 (Low) — `spec.instantiate()` is outside dispatch's error handling** (task_manager.py:208-209): a throwing plugin `__init__` propagates to the gateway caller as a raised exception instead of a rejected ack.

**L2 (Low) — identity check is loose substring matching** (device_manager.py:70-77): `cfg.vendor="NI"` matches any identity containing "ni".

**L3 (Low) — `wait()` on a still-queued task returns immediately** with QUEUED because `record.task` is None (task_manager.py:289-293), surprising for QUEUE-policy scripting.

**L4 (Low) — manifest git provenance uses `Path.cwd()`** (task_manager.py:378), so launching the app from another directory records wrong/no git state.

**L5 (Low) — `validate_boundary`'s `json.dumps(default=str)`** silently stringifies arbitrary payload objects before validation (contracts.py:91), which can convert a type error into a confusing downstream message.

UNCERTAIN: whether `stop()` implementations are all genuinely op-lock-bypassing (H4's blast radius depends on it) — that is controller-side and outside this assignment; and whether anything periodically drives `health_check_all()` (device_manager.py:224-230) so Suspenders on `device_health` actually receive data — I found no caller in core/bootstrap; confirming requires the UI/app layer.

## 4. Extension pain points

- **New instrument kind**: the factory/DI machinery is cleanly generic (factory.py:49-81, di.py:29-34), but a new kind touches four registration points (protocol, protocol→kind, factory, sim factory) with no single checklist; forgetting `register_capability_kind` fails only at first dispatch (di.py:83-87).
- **Reconnection/fault recovery** is the weakest axis: startup is all-or-nothing (`DeviceManager.start` raises on the first failed connect, device_manager.py:50-57), the resolver's inventory snapshot is frozen (M5), the reaper half-recovers (devices yes, run/records no — H4), and reaper-freed devices don't wake the queue (H5). There is no reconnect loop and no state through which a controller can be "offline but tolerated".
- **Web (Vue/Tauri) frontend**: the envelope/ack/event contracts are serialization-ready (closed `GatewayEvent` union, events.py:120-130) — good bones — but the prose-only ack reasons and the `reason=="final"` magic string (M6) would have to be re-parsed client-side, and there is no query API surface (`state_of`/`active_tasks` are Python methods, not commands) for a remote client to enumerate runs or replay state after reconnect.
- **New plugins**: the surface is genuinely small (plugin.py:15-45), but every plugin inherits the checkpoint-granularity trap: pause/cancel/heartbeat latency all equal the longest gap between checkpoints, and a single long awaited capability call silently disables all three (task_manager.py:105-116) — worth a documented budget or a controller-side heartbeat hook before more plugins are ported.
