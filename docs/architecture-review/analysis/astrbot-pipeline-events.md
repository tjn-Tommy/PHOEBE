# Panel report — Event dispatch & processing pipeline (AstrBot)

## 1. Design inventory

### 1.1 Ingestion: one shared unbounded queue, task-per-event dispatch

All platform adapters push events into a single `asyncio.Queue` via `Platform.commit_event()` → `put_nowait` (astrbot/core/platform/platform.py:147-149); the queue is created unbounded at startup (astrbot/core/core_lifecycle.py:195) and handed to every adapter. `EventBus.dispatch()` is an infinite loop that pops an event, resolves which pipeline configuration applies to its `unified_msg_origin` (UMO = `platform:msg_type:session_id`), and spawns **one `asyncio.Task` per event** (astrbot/core/event_bus.py:39-54). Two deliberate details: the bus keeps strong references to pending tasks in a set to prevent premature GC of pending tasks, and a done-callback re-raises otherwise-silent task exceptions into the log (event_bus.py:37, 56-63). There is **no concurrency limit, no backpressure, and no per-event timeout** anywhere in the dispatch path. Problem solved for AstrBot: chat events are independent and droppable-ish; maximum parallelism with minimal machinery.

Multiple pipeline instances exist simultaneously — one `PipelineScheduler` per config profile, selected per event by UMO (event_bus.py:42-51, core_lifecycle.py:433-445). This gives per-tenant/per-platform pipeline configuration without branching inside stages.

### 1.2 Stage model: registration, ordering, the onion

A stage is an ABC with `initialize(ctx)` + `process(event)` (astrbot/core/pipeline/stage.py:19-45). Registration is a trivial decorator appending the class to a module-global list (stage.py:10-16); actual registration happens by importing the stage modules, made idempotent by `ensure_builtin_stages_registered()` which checks an expected-name set before importing (astrbot/core/pipeline/bootstrap.py:34-49). Ordering is a **hardcoded list of class-name strings** (astrbot/core/pipeline/stage_order.py:3-13) applied by sorting the global list in every scheduler constructor (astrbot/core/pipeline/scheduler.py:20-26). The stage set is effectively closed: a stage not in `STAGES_ORDER` would crash `list.index`, and plugins cannot add stages — extensibility is instead provided by ~16 typed hook points (`EventType` enum, astrbot/core/star/star_handler.py:219-241) called *from within* stages via `call_event_hook` (astrbot/core/pipeline/context_utils.py:75-108).

The onion/interceptor model is the most distinctive mechanism. `Stage.process` may return either a plain coroutine (leaf: run, continue to next stage) or an **async generator**. For a generator, the scheduler drives it with `async for`, and at each `yield` **recursively executes all downstream stages** before resuming the generator (scheduler.py:43-76, recursion at :61). So `yield` means "flush the event's current result through the remainder of the pipeline, then return control to me" — a stage gets pre-processing, N mid-flushes, and post-processing in one function body. A handler that yields three replies causes decorate+respond to run three times. Short-circuiting is cooperative: `event.stop_event()` sets flags that the scheduler checks after every stage/yield (scheduler.py:54-76; flag implementation astrbot/core/platform/astr_message_event.py:340-362 — note *two* mechanisms, a `_force_stopped` bool plus a `result_type` enum on the result object, the former added because `clear_result()` erased the latter, per the comment at astr_message_event.py:56-57).

The same dual coroutine/generator convention is extended to plugin handlers by `call_handler` (context_utils.py:12-72): each value a handler yields is either a `MessageEventResult` (set as the event's result, then bare-`yield` to trigger a downstream flush) or passed upward as a value; a `_has_yielded` guard ensures generators that never yield still produce one pipeline continuation (context_utils.py:59-61).

### 1.3 The nine concrete stages (cross-cutting policy → work → egress)

Order (stage_order.py): waking check → whitelist → session status → rate limit → content safety → preprocess → process → result decorate → respond.

- **WakingCheckStage** is really "gating + command resolution": normalizes session identity per platform (astrbot/core/pipeline/waking_check/stage.py:17-32), assigns admin role (:97-100), decides wake (@-mention/prefix/private chat, :103-145), then evaluates every registered handler's filter chain, collecting `activated_handlers` and pre-parsed command params into `event._extras` (:160-235). Not-woken events are stopped (:237-238) — default-deny. Filter exceptions (e.g., bad command args) are converted into a user-facing message and stop the event (:187-195).
- **Whitelist / SessionStatus** are ~40-line predicate stages that call `event.stop_event()` (whitelist_check/stage.py:31-68).
- **RateLimitStage**: fixed-window limiter with a per-session timestamp `deque` and per-session `asyncio.Lock`, and two strategies — STALL (sleep inside the lock until the window frees) or DISCARD (astrbot/core/pipeline/rate_limit_check/stage.py:22-29, 60-85). Stalling deliberately serializes a flooding session while other sessions proceed.
- **ContentSafetyCheckStage**: strategy-selector over pluggable checkers (content_safety_check/strategies/strategy.py:6-34); notably re-invoked *by another stage* on LLM output (result_decorate/stage.py:139-156) — stage reuse as a library call.
- **PreProcessStage**: media normalization (download → local path → jpeg/wav) with each converted file registered to the event's temp-file tracker (preprocess_stage/stage.py:97-128), plus STT with a bounded retry loop for a platform race where the file isn't yet on disk (:186-205).
- **ProcessStage** delegates to sub-stages: plugin handlers first (`StarRequestSubStage`), then possibly LLM (process_stage/stage.py:33-67). Sub-stages are plain objects owned by the parent, not scheduler-registered (:20-26) — composition of the same Stage interface at a second level. A handler may yield a `ProviderRequest`, which ProcessStage routes into the agent sub-stage (:40-48).
- **StarRequestSubStage** runs activated handlers sequentially, clearing the result between handlers, catching all exceptions, firing an `OnPluginErrorEvent` hook, sending a user-facing error, and stopping the event (process_stage/method/star_request.py:36-74) — fault isolation per handler.
- **InternalAgentSubStage** wraps the LLM agent loop; relevant here: it serializes LLM work per session via a **ref-counted keyed lock manager** (internal.py:216; astrbot/core/utils/session_lock.py:8-31 — lock objects are created on demand and deleted when the refcount hits zero, with per-event-loop isolation :33-52), and its whole body is one try/except that converts any failure into a chat error message (internal.py:423-431).
- **ResultDecorateStage / RespondStage** split "transform result" from "transmit result". Decorate mutates `result.chain` in place: prefixes, reply-segmentation, TTS conversion, text-to-image, platform-specific packaging (result_decorate/stage.py:196-428). Respond validates non-emptiness with a per-component-type validator table (respond/stage.py:21-50), de-duplicates against already-sent texts (:182-204), hands streaming results to the platform adapter (:210-224), sends with per-send try/except (:253-313), and fires the after-sent hook (:315-318).

### 1.4 The event object and result accumulation

`AstrMessageEvent` is a mutable god-object carrying: raw text + structured message, platform metadata, session identity, role, wake flags, an **untyped `_extras` dict** used as the inter-stage side channel (astr_message_event.py:55; keys like `"activated_handlers"`, `"parsed_params"`, `"_streaming_finished"`), the single `_result: MessageEventResult` slot (:75), a trace span (:80-88), and a **temp-file ledger** — any stage may call `track_temporary_local_file()`, and `scheduler.execute()` deletes all tracked files in a `finally` regardless of outcome (astr_message_event.py:236-252; scheduler.py:94-96). Results are built with a fluent `MessageChain` builder over pydantic component models (message_event_result.py:17-192); `MessageEventResult` adds a stop/continue enum and a `result_content_type` distinguishing general/LLM/streaming results, plus an `async_stream` field so a producer stage can pass a live async generator through the pipeline to the respond stage (message_event_result.py:223-288, handoff respond/stage.py:210-224). Components override pydantic's `__repr_args__` to truncate base64 blobs in all logs (components.py:71-94). Send-back is `event.send(chain)`, abstract per platform (astr_message_event.py:475-492).

### 1.5 Session control (continuations) — two mechanisms

**session_waiter** (plugin API): a decorator creates a `SessionWaiter` keyed by a session-id in module-global `USER_SESSIONS`, and the calling handler awaits a `Future` (astrbot/core/utils/session_waiter.py:104-204). The continuation trigger is a **builtin plugin handler registered at maximum priority** that inspects every incoming event, and if its session matches a waiter, invokes the waiting handler with the new event and stops normal pipeline propagation (astrbot/builtin_stars/astrbot/main.py:42-49). Timeout is a `keep()`/`asyncio.Event` scheme where each keep spawns a `wait_for` holding task; expiry sets a `TimeoutError` on the future (session_waiter.py:40-82). So "wait for the user's next message" = park a future + hijack the next pipeline pass.

**Follow-up capture** (agent path): a per-UMO registry of active agent runners lets a *second* concurrent event inject its text into the running agent as a `FollowUpTicket` instead of starting a new run (process_stage/follow_up.py:161-200; ticket = seq + consumed flag + `asyncio.Event`, agent/runners/tool_loop_agent_runner.py:94-99). Unconsumed tickets fall through to normal processing, serialized in **strict arrival order** by an `asyncio.Condition` turn-taking state machine per UMO (follow_up.py:46-59, 111-148).

### 1.6 Error handling, timeouts, cancellation — summary of observed facts

One bad event does **not** kill the loop: each event is an isolated task whose exception is logged in the done-callback (event_bus.py:56-63). However, the `dispatch()` loop body itself has no try/except; an exception raised at event_bus.py:42 (`get_conf_info`) would terminate the dispatcher task, and since `run()` gathers tasks with `return_exceptions=True` (core_lifecycle.py:365), all event processing would halt with only a log entry. UNCERTAIN whether `get_conf_info` can actually raise — confirming requires reading `astrbot_config_mgr.py`. There is no per-event or per-stage timeout; cancellation is cooperative (`is_stopped()` polling) plus an external kill-switch: `active_event_registry` maps UMO → live events and supports both hard `stop_all()` and soft `request_agent_stop_all()` (a flag, so history saving still completes) (astrbot/core/utils/active_event_registry.py:28-64; registered around every pipeline run, scheduler.py:85-96). Point timeouts exist only where past incidents demanded them: tool-call timeout (internal.py:63), and a watchdog that closes a third-party streaming runner if nobody consumes its stream within N seconds (third_party.py:124-148), paired with an idempotent `close_runner_once` and stream cleanup in the generator's `finally` (third_party.py:218-233, 366-377).

### 1.7 Command parsing vs. plain events

Commands are not a separate ingress: they are handler filters evaluated during WakingCheck. `CommandFilter` introspects the handler signature at registration (star/filter/command.py:66-79), then at match time splits the message text and coerces each token to the annotated type (int/float/bool/Optional unwrap, `GreedyStr` for rest-of-line), raising human-readable usage errors (:93-173), and stashes the parsed kwargs in event extras (:218). Handlers are priority-sorted in the registry (star_handler.py:19-26). Plain (non-command) woken events fall through to the LLM path (process_stage/stage.py:53-67).

## 2. Quality observations

**Genuinely clean:** the scheduler itself — the entire onion model is ~40 lines of recursion (scheduler.py:43-76) and the Stage ABC is minimal; the strong-ref + done-callback task hygiene in EventBus; the ref-counted keyed lock manager (session_lock.py) — small, leak-free, loop-safe; the temp-file ledger tied to event lifetime with `finally` cleanup; `__repr_args__` log truncation; the third-party runner's watchdog/idempotent-close/finally triad — a compact resource-safety pattern clearly earned from leaks; the strategy-selector for content safety; per-handler fault isolation with an error *hook* so plugins can observe other plugins' failures (star_request.py:59-66).

**Organically grown / accidental complexity:** the `_extras` dict is a stringly-typed contract — pipeline correctness depends on magic keys (`"parsed_params"` is even popped mid-loop, waking_check/stage.py:226) with zero type checking; `ResultDecorateStage` is a 430-line conditional pile with hardcoded platform-name lists in three places (result_decorate/stage.py:205-209, 285-300, 396-407) and both it and RespondStage independently parse the same segmented-reply config (respond/stage.py:64-88); WakingCheck mixes five concerns; the stop-flag duality (`_force_stopped` vs. result enum) is a documented patch over a patch (astr_message_event.py:56-57); `ProcessStage.process` needs a `_t` sentinel to detect an empty generator (process_stage/stage.py:43-48); follow-up ordering state is a `dict[str, object]` unpacked with `assert isinstance` everywhere (follow_up.py:46-59) instead of a dataclass; `File.file` is a property that can *synchronously download* via `asyncio.run` (components.py:774-809); hooks catch `BaseException` and continue (context_utils.py:99-100); a base64-obfuscated blocklist of malicious hosts lives inline in the agent stage (internal.py:518-521). The comment noise (`workaround for #2309`, `may fix #2670`, napcat retry) shows policy accreted per incident rather than by design — honest, but these are exactly the parts not to copy.

## 3. Transferability triage (against PHOEBE's requirements)

**(a) Directly adoptable**
- Task hygiene: strong-ref set + done-callback exception surfacing (event_bus.py:37, 56-63). Phoebe spawns background tasks (writer flushes, previews); silent task GC/exception loss is the same hazard.
- Ref-counted keyed async lock manager (session_lock.py:8-31) — the cleanup idiom (drop the lock object when refcount hits zero) suits any per-run or per-resource keyed lock Phoebe adds beyond controller op-locks.
- Event-scoped resource ledger + `finally` cleanup (astr_message_event.py:236-252, scheduler.py:94-96) — run-scoped temp artifacts (intermediate masks, exported frames).
- Log-repr truncation of bulky payloads (components.py:71-94) — same idea as Phoebe's 256-point previews, applied to `repr`/logging so arrays never flood logs.
- Stream watchdog + idempotent close for never-consumed async streams (third_party.py:124-148, 366-377) — a UI that requests a preview stream and dies should not pin acquisition resources.
- Soft-stop vs hard-stop registry duality (active_event_registry.py:28-64) mirrors and validates Phoebe's stop-vs-pause split.

**(b) Adoptable with adaptations**
- The **generator-onion stage model** for a command-policy pipeline in front of `TaskManager.dispatch` (auth → interlock → rate policy → execute → record → ack). Adaptations required: typed stage context instead of `_extras` (Phoebe's `ContractModel` discipline); stage failure must produce a deterministic nack + `safe_state()` path, not log-and-continue; ordering as data is fine but validate the order/registration at startup rather than `list.index` at construction.
- **Command arg coercion UX** (command.py:93-173): Phoebe validates via pydantic already; the transferable part is turning validation failure into a usage string surfaced to the operator (waking_check/stage.py:187-195), not the hand-rolled coercion itself.
- **Rate limiting per key with pluggable strategy** (rate_limit_check/stage.py): for instruments the right strategies are *coalesce/latest-wins* (UI slider spam to SLM), not STALL — sleeping while holding the per-key lock (rate_limit_check/stage.py:60-79) would head-of-line-block a hardware queue.
- **session_waiter's controller** (future + keep/timeout, session_waiter.py:18-87) is a good skeleton for "wait for operator confirmation mid-run" as an extension of `ctx.checkpoint`. Do *not* copy the trigger mechanism (module-global dicts + a max-priority handler hijacking the pipeline, builtin main.py:42-49); route it through the Gateway as an explicit command type.
- **Strict arrival-order turn-taking** (follow_up.py:46-148) matches Phoebe's `dispatch_policy=queue` fairness needs; reimplement over a dataclass, not `dict[str, object]`.
- **Streaming handoff via a result field** (message_event_result.py:243; respond/stage.py:210-224): the "producer sets an async generator, egress stage decides transport" split maps to controller→UI preview streams — but add bounding; AstrBot's version has none.
- **Per-config pipeline instances routed by origin** (event_bus.py:42-51) ≈ per-instrument-profile pipelines; Phoebe's TOML-per-instrument config already provides the routing key.

**(c) Unsuitable — domain break**
- **Unbounded queue + task-per-event unlimited concurrency** (platform.py:149; event_bus.py:52): chat events for different users are independent; instrument commands are not. Phoebe requires serialized per-instrument access and must-deliver acks — copying this scheduler would race hardware. Phoebe's Gateway/TaskManager + leases is the correct replacement, not an adaptation target.
- **Log-and-continue inside policy stages and hooks** (context_utils.py:99-100; respond/stage.py per-send swallow :276-313): acceptable when the cost is a lost chat message; in lab control a failed check must abort and drive `safe_state()`.
- **Mutable god-event with untyped extras as the inter-stage contract** (astr_message_event.py:55): directly contradicts Phoebe's frozen `ContractModel`/`validate_boundary` choke points; the extras dict is the single largest source of hidden coupling in this codebase.
- **Cooperative-only stop flags with dual sources of truth** (astr_message_event.py:340-362): Phoebe's explicit run state machine with a final rebroadcast is strictly stronger; regressing to mutable booleans would reintroduce ordering races.
- Chat-specific stages (waking, whitelist-as-chat-ACL, content safety, TTS/t2i decoration) have no direct analog; only their *shape* (cross-cutting policy stages) transfers, per (b).

## Extension pain points / notable ideas

Pain points to avoid: closed stage set with string-name ordering means adding a stage touches three files (stage_order.py, bootstrap.py, the stage) and any omission is a runtime crash; the extras-dict contract makes stage reordering silently unsafe; no supervision of the dispatcher task itself (a single uncaught exception in the loop body silently stops the world). Ideas worth stealing wholesale: hook points as the plugin extension surface *instead of* letting plugins add pipeline stages (keeps ordering closed and auditable — matches Phoebe's "plugins contain zero locks" philosophy); `yield`-as-flush giving handlers incremental result emission without exposing the transport; the incident-driven micro-timeouts (watchdog, STT retry) as a checklist of where async pipelines actually leak in production.
