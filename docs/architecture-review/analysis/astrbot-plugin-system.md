# AstrBot Star (Plugin) System — Architecture Analysis

Scope: `astrbot/core/star/` (all files read in full), `astrbot/api/` façade, `astrbot/builtin_stars/{builtin_commands,astrbot}` as authoring examples, plus the dispatch-side consumers (`astrbot/core/pipeline/waking_check/stage.py`, `astrbot/core/pipeline/process_stage/method/star_request.py`, `astrbot/core/pipeline/context_utils.py`) and `astrbot/core/utils/pip_installer.py` read to verify claims.

## 1. Design inventory

**1.1 Discovery: convention-based directory scan, no entry points.** Plugins live in two roots: user plugins in `data/plugins/` and "reserved" builtins in `astrbot/builtin_stars/` (astrbot/core/star/star_manager.py:192-199). `_get_modules` scans each subdirectory for `main.py` or `<dirname>.py` (star_manager.py:276-301); reserved plugins are flagged so they cannot be uninstalled (star_manager.py:307-311, 1671-1672). Import is plain `__import__("data.plugins.<dir>.main")` (star_manager.py:438) — it works because startup pushes the AstrBot root onto `sys.path` (main.py:77-79), making `data` an implicit namespace package. There is **no module isolation**: all plugins share one interpreter, one `sys.modules`, one site-packages. Identity is by dotted module path throughout; every registry is keyed or cleaned by the `data.plugins.<dir>` prefix (star_manager.py:676-692). A `metadata.yaml` (name/author/desc/version required, validated: astrbot/core/star/updator.py:113-150) provides display metadata, a PEP 440 `astrbot_version` compat range, i18n bundles, and UI pages (star_manager.py:466-538); the metadata `name` is validated as a legal Python identifier because it becomes the on-disk/import directory name (star_manager.py:582-623).

**1.2 Registration: import-time side effects into module-level globals.** Two global registries — `star_registry: list[StarMetadata]` and `star_map: dict[module_path, StarMetadata]` (astrbot/core/star/star.py:9-11). Since v3.5.19 the plugin class self-registers via `Star.__init_subclass__`, which creates a skeleton `StarMetadata(star_cls_type=cls, module_path=cls.__module__)` at class-definition time (astrbot/core/star/base.py:38-49); the older `@register_star` decorator survives as a deprecated shim that fills the same dict (astrbot/core/star/register/star.py:8-66). Loading is therefore **two-phase**: importing the module populates the registries as a side effect; `PluginManager.load()` then finds the entry in `star_map`, merges YAML metadata (YAML wins, star_manager.py:1129-1144), checks the version specifier (star_manager.py:1150-1160), attaches per-plugin config parsed from `_conf_schema.json` (star_manager.py:1107-1121), instantiates the class — trying `(context, config)` then falling back to `(context)` on `TypeError` (star_manager.py:1176-1188) — and finally calls `await initialize()` (star_manager.py:1346-1347). A pre-v3.4 legacy path instead heuristically hunts for a class named `*Plugin` or `Main` (star_manager.py:265-274, 1236-1295).

**1.3 Handler registration and late instance binding.** Every decorator (`@filter.command`, `@filter.regex`, `@filter.on_llm_request`, …, exposed under short names via the façade) funnels into `get_handler_or_create`, which builds a `StarHandlerMetadata` keyed by `f"{module}_{name}"` and appends it to the global `star_handlers_registry` (astrbot/core/star/register/star_handler.py:31-72). The key insight: the metadata is **created once per function and shared across stacked decorators** — each additional decorator just appends another filter to `handler_md.event_filters` (e.g. register/star_handler.py:119-120, 300, 323-326), so `@permission_type(...)` + `@command(...)` compose (astrbot/builtin_stars/builtin_commands/main.py:38-42). Decorators capture the **unbound** function; the `self` binding happens at load time by mutating the metadata: `handler.handler = functools.partial(handler.handler, metadata.star_cls)` for every handler whose `__module__` equals the plugin's main module path (star_manager.py:1205-1215). A hidden consequence: decorated handlers must live in the plugin's entry module — `builtin_commands` obeys this by declaring thin `@filter.command` methods in `main.py` that delegate to command classes in a subpackage (builtin_stars/builtin_commands/main.py:28-36). The registry keeps handlers sorted by a `priority` stored in a loose `extras_configs` dict, re-sorting on every append (astrbot/core/star/star_handler.py:19-26).

**1.4 Filters: a small declarative predicate object model.** `HandlerFilter` is a one-method ABC, `filter(event, cfg) -> bool` (astrbot/core/star/filter/__init__.py:8-12). Concrete filters: command (with signature-derived argument parsing), command group (a tree of sub-filters, command_group.py:22-33), regex, message type, platform type, permission, and user-defined `CustomFilter` whose metaclass overloads `&`/`|` for boolean composition (astrbot/core/star/filter/custom_filter.py:9-34). `CommandFilter.init_handler_md` inspects the handler's signature, skipping `self` and `event`, and records annotation-or-default per parameter (filter/command.py:66-79); at match time it tokenizes the message and coerces types, including a `GreedyStr` marker type meaning "consume the rest" (filter/command.py:15, 102-114); parsed params are stashed on the event as `parsed_params` (filter/command.py:218). Matching a bare command group raises `ValueError` carrying a rendered help tree of its subcommands (filter/command_group.py:125-133) — errors double as help output.

**1.5 Dispatch: broadcast filter scan, then sequential contained execution.** `WakingCheckStage` iterates **every** `AdapterMessageEvent` handler and requires all its filters to pass (AND), with permission filters special-cased to produce a "no permission" reply instead of a silent skip (astrbot/core/pipeline/waking_check/stage.py:160-226). Survivors are stored on the event (`activated_handlers`, `handlers_parsed_params`, stage.py:234-235), filtered again by per-session plugin disable lists (astrbot/core/star/session_plugin_manager.py:49-101). `StarRequestSubStage` then runs them in priority order; each handler executes inside try/except — on exception it logs the traceback, fires an `OnPluginErrorEvent` hook so other plugins can intercept, sends the user an error message, and stops the event (astrbot/core/pipeline/process_stage/method/star_request.py:47-74). `call_handler` normalizes plain coroutines and async generators into one generator protocol (yield = send intermediate result — an "onion model" letting a handler emit multiple replies) (astrbot/core/pipeline/context_utils.py:12-72); `call_event_hook` catches `BaseException` per hook so one bad hook cannot break the chain (context_utils.py:92-101).

**1.6 Lifecycle, enable/disable, hot reload.** `Star` defines `async initialize()` / `async terminate()` (base.py:81-88); legacy `__del__` is still honored, run in an executor with a done-callback logging exceptions (star_manager.py:1889-1906). Disable persists the module path into a shared-preferences list `inactivated_plugins` and deactivates the plugin's LLM tools (star_manager.py:1850-1874); crucially, a disabled plugin's module is still imported and registered on next boot but the class is **never instantiated** (star_manager.py:1173-1195), and dispatch checks `plugin.activated` per lookup (star_handler.py:163-167). Hot reload is opt-in (`ASTRBOT_RELOAD=1`) via `watchfiles.awatch` over both plugin roots; a change reloads the owning plugin (star_manager.py:210-263). Reload = terminate → `_unbind_plugin` (delete from `star_map`/`star_registry`, remove handlers, remove LLM tools by module-path prefix, unregister platform adapters) → purge every `sys.modules` entry under the plugin's module prefix → re-import (star_manager.py:967-1021, 1768-1829, 694-726). A parallel `_cleanup_plugin_state` handles half-loaded failures (star_manager.py:728-769). All manager operations serialize on one `asyncio.Lock` (star_manager.py:203-204, used at 950, 980, 1556, 1667, 1716, 1856).

**1.7 Failure records.** Any `BaseException` during a plugin's load is caught per plugin; a rich failure record (error, traceback, whatever metadata could still be read) goes into `failed_plugin_dict` (star_manager.py:1362-1378, 771-808), which powers a human-readable summary (star_manager.py:810-833) and dedicated `reload_failed_plugin` / `uninstall_failed_plugin` flows (star_manager.py:939-965, 1709-1766). One broken plugin never blocks the rest.

**1.8 Dependency installation.** Each plugin may ship `requirements.txt`, installed at install/update/import-failure time. A pre-check plans which requirements are actually missing and writes a **trimmed temporary requirements file** so satisfied deps aren't reinstalled (star_manager.py:134-178, 101-131). Import failures trigger a small recovery state machine (DISABLED / PRELOAD_AND_RECOVER / RECOVER_ON_FAILURE / REINSTALL_ON_FAILURE, star_manager.py:85-96, 362-464): retry the import after preferring already-installed site-packages, else reinstall and retry. pip itself runs **in-process** (`pip._internal.cli.main` on a worker thread, astrbot/core/utils/pip_installer.py:1056-1068), with a constraints file pinning core dependencies so plugin installs can't break AstrBot itself (pip_installer.py:1018-1020), conflict classification into typed exceptions (pip_installer.py:54-70), credential redaction in logs (pip_installer.py:135-185), and a `--target data/site-packages` scheme only for the packaged desktop runtime (pip_installer.py:1001-1016). There is **no per-plugin environment isolation** — all plugins share one dependency namespace.

**1.9 Context, StarTools, and the api/ façade.** `Context` is the capability object handed to every plugin: ~30 methods spanning provider lookup, LLM/agent invocation, active message sending, tool registration, DB access, config access (astrbot/core/star/context.py:122-751), including deliberate SDK-style versioned additions (`.. versionadded:: 4.5.7`, context.py:184, 232). It performs no per-plugin supervision — any plugin can reach any manager. `StarTools` is a static utility façade over the same context; notably `get_data_dir()` walks the **call stack** to infer which plugin is calling and allocate `data/plugin_data/<plugin>` (astrbot/core/star/star_tools.py:206-260). The public surface is re-exported under `astrbot/api/`: `api/star/__init__.py:1-7` (Star, Context, register), `api/event/filter/__init__.py:11-41` renaming `register_command` → `command` etc., and a legacy wildcard `api/all.py`. Plugins import only `astrbot.api.*` (builtin_stars/builtin_commands/main.py:1-2), so core internals can move as long as the façade re-exports hold. Version compat toward plugins is the PEP 440 `astrbot_version` specifier checked at load (star_manager.py:625-657); API-side compat is handled by deprecation shims kept alive (register_star; deprecated Context methods at context.py:600-751).

**1.10 Runtime command administration.** A WebUI-facing layer builds `CommandDescriptor`s from the live registry, persists renames/aliases/enable-state/permission to a DB table, and applies them by **mutating the live filter objects** (`filter_ref.command_name = ...`, invalidating the name cache) plus `handler.enabled` (astrbot/core/star/command_management.py:434-496); a legacy `alter_cmd` preference can inject `PermissionTypeFilter`s into handlers at load time (star_manager.py:1312-1341). Conflict detection groups enabled commands by effective name (command_management.py:462-469).

## 2. Quality observations

**Genuinely clean:** the filter object model (small ABC, composable, testable in isolation); the idempotent `get_handler_or_create` enabling decorator stacking; layered error containment (per-filter → per-handler → per-hook → per-plugin-load) with the failure-record + retry UX; the trimmed-requirements precheck and core-constraints file; archive metadata validation *before* extraction (updator.py:152-206); the api/ façade discipline; the explicit `versionadded` annotations on Context methods.

**Organically grown / accidental complexity:**
- `PluginManager.load()` is a ~380-line method carrying **two full registration code paths** (subclass-hook and pre-v3.4 heuristic class discovery) inline (star_manager.py:1023-1405), plus metadata merging, version gating, config loading, instance binding, tool binding, and permission injection. `star_manager.py` is 2,044 lines total.
- `StarMetadata` has ~20 fields, nearly all `None`-defaulted and mutated incrementally across import, load, and YAML merge (star.py:17-76) — no invariant is enforceable at any point; the docstring itself warns "when activated is False, star_cls may be None" (star.py:19-22).
- The `functools.partial` self-binding permanently mutates shared registry state; correctness depends on cleanup always running before re-load (a double `load()` without purge would double-bind). Class attributes are injected by `setattr` before instantiation (star_manager.py:1166-1171) — stringly, invisible to type checkers.
- `register_custom_filter` distinguishes bare command / subcommand / group by `isinstance` checks on its *first positional argument*, and contains a condition `(not A and B) or (A and B)` that is just `B` (register/star_handler.py:139-198, 156-159).
- `CommandFilter.handler_params` conflates "annotation" and "default value" in a single dict slot, and the converter branches on which it got (filter/command.py:69-79, 100-168).
- Thirteen near-identical `@overload`s on `get_handlers_by_event_type` (star_handler.py:32-148) buy little type precision for a lot of noise; `priority` living in a raw dict rather than a field is similar looseness.
- `_cleanup_plugin_state` contains two consecutive loops that remove metadata from `star_registry` under overlapping conditions (star_manager.py:739-753) — visible scar tissue from bug-fixing.
- Reload leak surface: `Context.registered_web_apis` is a **class variable** never cleaned by `_unbind_plugin` (context.py:125, 568-590), and `_register_tasks` likewise (context.py:128, 741-751); a failed `terminate()` merely logs a warning and proceeds to yank the module (star_manager.py:992-998).

## 3. Transferability triage

**(a) Directly adoptable by PHOEBE:**
- **Failed-plugin records with retry/uninstall flows** (star_manager.py:206-209, 771-833, 939-965): PHOEBE loads experiment plugins at startup; keeping a structured per-plugin failure record (error + traceback + metadata) surfaced in the UI, with "reload this one plugin" — rather than pass/fail of the whole app — directly serves the reliability requirement.
- **Layered error containment at the dispatch boundary** (star_request.py:47-74, context_utils.py:92-101): per-handler try/except that logs, emits an internal error event, informs the user, and halts only that run maps cleanly onto TaskManager's run failure path; the "OnPluginErrorEvent hook lets another plugin observe failures" idea is a cheap, decoupled way to add e.g. an experiment-failure notifier.
- **PEP 440 `phoebe_version` specifier in plugin metadata** checked at load with a clear message (star_manager.py:625-657): trivially portable, prevents silent API drift once external experiment plugins exist.
- **The api/ façade pattern** (api/star/__init__.py, api/event/filter/__init__.py): a `phoebe.api` module re-exporting `register`, `on_command`, `Depends`, contract types under stable names would let core refactor freely — PHOEBE plugins currently import from `phoebe.plugins`/core paths directly.
- **Metadata validation before extraction/installation** (updator.py:152-206) if PHOEBE ever installs plugins from archives.

**(b) Adoptable with adaptations:**
- **Hot reload via file-watch + module-prefix purge** (star_manager.py:210-263, 694-726): highly valuable for iterating on experiment plugins against the sim backend. Adaptation required: AstrBot tolerates a failed `terminate()` and reloads anyway (star_manager.py:992-998); PHOEBE must not — reload must be refused (or forced through controller `safe_state()`/lease revocation) while the plugin has a RUNNING run or held leases, because a purged module can leave an instrument mid-sweep. The prefix-keyed cleanup (every registry entry carries its owning module path: star_handler.py:260-261, star_manager.py:756-769) is the transferable *precondition* for reload — PHOEBE's `@register` registry would need the same ownership metadata. The observed leaks (class-variable registries, context.py:125) are the checklist of what *not* to do.
- **Enable/disable without instantiation** (star_manager.py:1173-1195, persisted list at 1042): maps to disabling an experiment plugin without unloading; adaptation is that PHOEBE bindings (`[plugins."<id>".bindings]`) should also be released on disable. Session-scoped disabling (session_plugin_manager.py) is chat-specific but its shape maps to per-config plugin sets.
- **Dependency handling**: the core-constraints file (pip_installer.py:1018-1020) is the important idea — a lab platform must protect pinned `pyvisa`/`nidaqmx`/vendor-SDK versions from plugin installs. The missing-deps precheck and trimmed temp requirements (star_manager.py:101-178) are portable. Run pip in a subprocess instead of in-process (pip_installer.py:1056-1068 mutates `sys.path`, root logging handlers, and environ locks — star_manager.py:1393-1395 even has to scrub logging handlers pip leaks); an interpreter driving live hardware should not run pip's code in-process.
- **Decorator → metadata-object registration with stacking** (register/star_handler.py:38-72): PHOEBE's `@on_command` already resembles this; the adoptable increments are (i) the idempotent shared-metadata trick allowing orthogonal decorators (e.g. `@requires(role=...)`, `@ui_hint(...)`) to compose, and (ii) declarative predicate objects instead of imperative checks. But keep registration keyed per-app-instance rather than AstrBot's process-global lists if test isolation matters (PHOEBE's offline pytest suite would suffer from cross-test registry bleed; AstrBot mitigates only via `clear()`, star_handler.py:201-203).
- **Runtime command reconfiguration persisted to DB** (command_management.py): the concept (UI-editable command names/permissions overlaying code-declared defaults, with conflict detection) transfers to renaming experiment commands per lab; prefer rebuilding registry entries over mutating live filter objects.

**(c) Unsuitable — chat-domain assumptions break:**
- **Broadcast filter-scan dispatch** (waking_check/stage.py:160-226): every message probing every handler's filter chain is right for chat, where *which* handler should fire is fuzzy (prefixes, mentions, regex) and fan-out to multiple handlers is desired. PHOEBE commands are explicitly addressed (`CommandEnvelope` → one capability), must-deliver, and serialized per instrument; O(N) speculative matching and multi-handler wake semantics would blur command ownership and fight the lease model.
- **`functools.partial` instance binding by mutating the registry** (star_manager.py:1211-1215) and the "handlers must live in the entry module" constraint it imposes: PHOEBE's DI (`Depends(role=...)` resolved at dispatch, core/di.py) is strictly better; don't regress.
- **Stack-frame caller inference** (star_tools.py:226-242): implicit, breaks under wrapping/threading; PHOEBE's `ctx` already identifies the plugin explicitly.
- **`__del__` as a lifecycle hook** (base.py:87-88, star_manager.py:1889-1906) and constructor-signature sniffing via `TypeError` fallback (star_manager.py:1176-1188): legacy accretions, not designs.
- **God-object Context** (context.py:122-751): AstrBot can afford an unsupervised all-access capability object because the blast radius of a misbehaving chat plugin is a bad message. PHOEBE's fault-isolation and serialized-access requirements are exactly why its narrower `ctx` + role-scoped instrument injection exists; do not widen it to Context-style ambient authority.

## 4. Extension pain points / notable ideas

Pain points to avoid inheriting: monolithic `load()` mixing two eras of registration; metadata-by-mutation with no valid-state invariant; global singleton registries; cleanup logic duplicated between `_unbind_plugin` and `_cleanup_plugin_state`. Ideas worth stealing beyond §3: the **async-generator handler protocol** (context_utils.py:44-61) — a plugin `yield`ing intermediate results that the framework routes onward is a neat fit for experiment plugins emitting progress/preview points through `ctx` without new API surface; the **error-as-help** pattern where a bare command group raises its own subcommand tree (command_group.py:125-133); and `session_waiter` used by a max-priority handler to implement "wait for the user's next input" (builtin_stars/astrbot/main.py:42-49, 112-135) — structurally similar to an operator-confirmation checkpoint in an experiment run.

UNCERTAIN items: whether double-`load()` without purge can double-apply the `functools.partial` binding in practice (would need a trace of `install_plugin` racing `reload`; the `_pm_lock` probably prevents it, star_manager.py:203); whether `registered_web_apis` leakage is observable in production (needs a reload test with a web-API-registering plugin).
